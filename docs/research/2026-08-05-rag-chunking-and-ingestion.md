# RAG chunking and ingestion — source-grounded notes

**Date:** 2026-08-05 · **Sources:** cited inline, primary sources preferred over blog summaries where
fetched directly.

## 1. MAF has no chunking implementation to draw from

Confirmed by direct repo inspection (`D:\GitSrc\agent-framework`, local checkout), not assumed: a
grep for `Splitter`/`chunk_size`/`ChunkText`/`TextSplit`/`RecursiveCharacter` across the whole tree
returns only conversation-evaluation splitting (`IConversationSplitter.cs`,
`Evaluation_ConversationSplits`) — unrelated to document/RAG chunking. `TextSearchProvider`
(`dotnet/src/Microsoft.Agents.AI/TextSearchProvider.cs`) takes an opaque search delegate and never
touches raw documents. The one concrete chunk/upsert implementation in the repo,
`dotnet/samples/02-agents/AgentWithRAG/AgentWithRAG_Step01_BasicTextRAG/TextSearchStore/TextSearchStore.cs`,
is explicitly marked "provided as a sample implementation, but may be promoted to a first-class
supported API" (lines 18-19) and its `UpsertTextAsync`/`UpsertDocumentsAsync` methods take
already-chunked text — there is no splitter anywhere in MAF, sample included. **This design has no
MAF precedent to port; the strategy below is drawn from primary RAG-chunking research instead.**

## 2. Chunking strategies — what the evidence actually supports

Fetched directly from Anthropic's own engineering post
([anthropic.com/engineering/contextual-retrieval](https://www.anthropic.com/engineering/contextual-retrieval)):

- **Contextual Retrieval method**: before embedding/indexing, prepend each chunk with 50-100 tokens
  of chunk-specific context generated by having Claude read the *whole* document and the chunk
  together and "give a short succinct context to situate this chunk" — done once for **contextual
  embeddings** and again for **contextual BM25** (the same prepended text feeds both the vector
  index and a lexical index).
- **Measured accuracy** (top-20-chunk retrieval failure rate, baseline 5.7%): contextual embeddings
  alone → 3.7% (**35% reduction**); + contextual BM25 → 2.9% (**49%**); + reranking → 1.9% (**67%**).
- **Cost**: "$1.02 per million document tokens" one-time preprocessing, using prompt caching — i.e.
  the whole-document-context step is cheap only because of caching the document across many chunk
  calls, not free.
- **Explicit scope limit, stated by Anthropic itself**: for a knowledge base under ~200,000 tokens
  (~500 pages), skip retrieval entirely and put the whole thing in context — contextual retrieval
  (and by extension, this whole chunking pipeline) is a **large-corpus mechanism**, not a default for
  every knowledge base regardless of size.
- Anthropic states chunk size/boundary/overlap affects results but does not fix a number, and closes
  with "always run evals" on the specific corpus — i.e. no single chunking config is claimed correct
  in general.

Cross-checked against a second primary source, Chroma's own published chunking-strategy research
([research.trychroma.com](https://research.trychroma.com), via
[firecrawl.dev's summary](https://www.firecrawl.dev/blog/best-chunking-strategies-rag), fetched
2026-08-05): recursive-character splitting at 400 tokens scores 88.1-89.5% recall; semantic chunking
(LLM- or cluster-based) scores 91.3-91.9% — a real but small (2-4 point) edge, and Chroma's own
number shows **up to a 9-point recall swing** between the best and worst strategy on the *same*
corpus, i.e. strategy choice matters more than any single strategy's absolute number. A third,
independently-run benchmark cited in the same summary (Vecta, Feb 2026) found the *opposite*
ranking — recursive splitting beating semantic chunking (69% vs. 54%) — on a different corpus and
task. **Evidence across sources conflicts on which strategy wins**, which corroborates rather than
undermines Anthropic's "always run evals" guidance: no single chunking strategy is a safe universal
default claim, only a safe *starting point*.

**Working synthesis, holding only what's corroborated across sources, not the disputed edge case**:

1. **Default starting point**: recursive/structure-aware splitting (paragraph → line → sentence
   fallback, or a format-aware split for code/markdown/HTML), token-bounded (not character-bounded,
   since embedding and chat-model limits are token limits) at roughly 400-512 tokens with 10-20%
   overlap. This is corroborated as a reasonable default across every source found, disputed only on
   whether semantic chunking beats it — not on whether it's a defensible baseline.
2. **Semantic/contextual chunking is a strictly optional upgrade**, gated behind an actual eval
   showing it helps on the operator's own corpus — never a default, given the conflicting evidence
   above and the nonzero cost (chunk-context generation is a model call).
3. **Chunking strategy choice should be swappable, not hardcoded** — the magnitude of the
   cross-strategy variance (up to 9 points on identical data) means a fixed, unconfigurable choice is
   itself a design risk independent of which one is picked.

## 3. NVIDIA's 2024 benchmark — query-type sensitivity

Cited via the same firecrawl.dev summary (original: NVIDIA, 2024, seven chunking strategies across
five datasets): page-level chunking had the lowest variance (0.648 accuracy, 0.107 std. dev.) across
query types, but factoid queries did best with smaller chunks (256-512 tokens) while analytical
queries needed larger ones (1024+ tokens) — another data point against a single fixed chunk size,
this time by query type rather than corpus type. Not independently re-verified against NVIDIA's own
paper; flagged as secondary-sourced, included because it corroborates the "make it configurable"
conclusion from an unrelated angle.

## 4. Graph-structured retrieval (GraphRAG-style)

Fetched directly from Microsoft's own GraphRAG documentation
([microsoft.github.io/graphrag](https://microsoft.github.io/graphrag/), published originally by
Microsoft Research, April 2024, this page fetched 2026-08-05):

**Indexing pipeline, in order, with each stage's LLM-vs-deterministic status stated explicitly by
the source:**

1. **Text slicing into TextUnits** — pure algorithmic, no model call.
2. **Entity/relationship/claim extraction per text unit** — LLM call.
3. **Hierarchical clustering (Leiden algorithm)** over the extracted entity graph — pure
   deterministic algorithm, no model call.
4. **Community summarization**, bottom-up over the Leiden hierarchy — LLM call.

**Stored artifacts**: entities (with graph-degree metrics), relationships, claims, and
hierarchical community reports — all structured records, not raw vectors.

**Query modes**, from the same source and cross-checked against
[microsoft.github.io/graphrag/query/local_search](https://microsoft.github.io/graphrag/query/local_search/):
**local search** (identify entities semantically related to the query, traverse to connected
entities/relationships/community reports — an entity-centric, on-demand lookup), **global search**
(reason over community summaries for holistic, corpus-wide questions a single-entity lookup can't
answer), **DRIFT search** (a community/vector search first, generating follow-up questions answered
by local search — a hybrid of the two).

**Cost and scale, cross-checked against a second source**
([callsphere.ai/blog/vw6g-microsoft-graphrag-knowledge-graph-2026](https://callsphere.ai/blog/vw6g-microsoft-graphrag-knowledge-graph-2026),
2026): Microsoft's reference implementation costs roughly **$20-40 per million document tokens** to
index with GPT-4o-class models — community summarization (stage 4) is the expensive step. A lighter
variant (LightRAG) that **skips precomputed community summaries** and does dual-level retrieval
directly over the graph instead reports comparable-or-better accuracy on the same holistic-query
class for roughly **$0.50 per million tokens** — a 50-6000x cost difference for a large chunk of the
same benefit, by dropping exactly the one LLM-heavy stage. Both sources place GraphRAG's useful
range at roughly 1,000-1,000,000 corpus tokens; below that, plain retrieval (or no retrieval at all,
per §2's Anthropic citation) is simpler, and past it a lighter graph variant or a different mechanism
is the cited recommendation, not a claim this project independently verified.

**Relevance to a from-scratch spec**: the LLM-call/deterministic-algorithm split lines up exactly
with the split §2 above already needed for chunking (structural = deterministic, contextual =
attributed model call) — graph extraction and community summarization are two more instances of the
same distinction, not a new one, and Leiden clustering is a third deterministic stage alongside
recursive/structure-aware chunking. The cost gap between GraphRAG and LightRAG is the same
"strategy choice matters, evidence doesn't converge on one winner" lesson §2 draws for chunking,
now with a concrete cost axis (dropping precomputed summarization is nearly free and reportedly
loses little accuracy on the cited benchmark) rather than only an accuracy axis.

## 5. Document-shape-specific extraction (papers, invoices, drawings, spreadsheets, DOCX, PPT)

Fetched directly ([firecrawl.dev/blog/best-pdf-parsers](https://www.firecrawl.dev/blog/best-pdf-parsers),
2026) plus a second search pass
([llamaindex.ai/insights/best-ocr-for-invoices](https://www.llamaindex.ai/insights/best-ocr-for-invoices),
[extend.ai/resources/invoice-ocr-layout-aware-parsing](https://www.extend.ai/resources/invoice-ocr-layout-aware-parsing),
2026):

**Three extraction tiers exist, not one**, confirmed directly from the primary source's own
distinctions:

1. **Text-layer extraction** — "reads embedded text from PDF internals" (or the equivalent for
   DOCX/PPTX/XLSX's own XML-based formats). Deterministic, but blind to scanned/image-only content —
   "parsers without OCR return blank content" on those pages.
2. **OCR** — "renders pages as images, then reads the text from the pixels." Necessary for scanned
   invoices, blueprints, and image-heavy PDFs; imperfect (misreads happen) but not a `ChatClient`
   call — closer to a lossy codec than a model call.
3. **VLM/neural layout-aware extraction** — "uses layout models to detect structure before
   extracting," and the same source states plainly: **"VLM-based parsers can hallucinate content in
   high-resolution, text-dense scenarios."** This tier is a genuine model call, used where tiers 1-2
   can't recover table/form structure correctly.

**Docling** (IBM/Linux Foundation, Apache 2.0, 37k+ GitHub stars, Granite-Docling-258M VLM
component released January 2026) produces one structural representation —
`DoclingDocument`, capturing "layout, reading order, table cell boundaries, formula positions, and
image placement" — across PDF, DOCX, PPTX, XLSX, HTML, images, LaTeX, and plain text under a single
API, exporting to Markdown/HTML/JSON/DocTags. Compared against **MarkItDown** (Microsoft): Docling
scores higher on table-extraction accuracy (88% vs. 82% F1 per one cited benchmark) while MarkItDown
is faster (~12s/100 pages) and covers more formats (15+ vs. ~6) — no single tool wins on every axis,
the same pattern already found for chunking and graph strategies.

**Invoices/forms specifically** use tier-3 (VLM-based layout-aware) extraction to go directly to
labeled structured fields — vendor, invoice number, date, totals, line items — without a
hand-authored template per vendor layout, per both invoice-OCR sources cited above.

**Relevance to a from-scratch spec**: the three-tier split maps onto the determinism/attribution
discipline already established for chunking (§2) and graph extraction (§4) — tiers 1-2 are the
deterministic default path, tier 3 is the attributed, budgeted, determinism-waived path, a fourth
instance of the same pattern rather than a new one. The stated hallucination risk in tier 3 is not
just an accuracy concern: content a VLM extractor invents that never appeared in the source document
is model output being treated as document content, which is the exact authority-laundering shape a
determinism-and-attribution discipline exists to catch — extraction output from tier 3 needs
distinct provenance from tiers 1-2, not silent merging as if both were equally literal
transcriptions.
