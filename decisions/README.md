# Decisions — the ADR record

An **ADR** here is not a memo. It is the durable record of a `design → red-team → prove → judge`
loop: competing designs implemented in real C++23, attacked adversarially, compiled under multiple
compilers, run under sanitizers, and measured — before a judge picks a winner on evidence.

This is the process Quark uses (36 ADRs and counting), and it exists because the alternative —
settling a hot-path or security-critical question by argument — produces designs that read well and
fail under load or attack.

## When an ADR is required

- Any **security-critical** choice: capability representation, isolation boundary, taint mechanism,
  approval binding, secret handling.
- Any **hot-path** choice measured by a 023 budget.
- Any choice where **credible designs disagree** and the disagreement is not resolvable by reading.
- Any **promotion** of an RFC from Draft to Proven — the gate execution *is* the ADR.

Ordinary implementation choices do not need one. An ADR for everything is an ADR for nothing.

## What an ADR must contain

1. **The question**, stated so that it has a wrong answer.
2. **The competing designs**, each steelmanned.
3. **Falsifiable claims** per design — specifically the fast/safe/correct claims, each paired with
   an experiment that would *disprove* it.
4. **The red-team attack** on each design, hardest where it claims to be fast or safe.
5. **The executed evidence**: commands, compilers, sanitizers, measured numbers (percentiles, not
   means), with **positive controls** — a test that cannot fail proves nothing, and for security
   claims this is mandatory (022 §5).
6. **Per-claim verdicts**: CORRECT / WRONG / INCONCLUSIVE, decided by observed output, not argument.
   `INCONCLUSIVE` is an honest verdict and must not be laundered into either of the others.
7. **The decision**, the specs it binds, and the residual risks or deferred gates.

## Naming

`ADR-NNN-<kebab-case-question>.md`, numbered sequentially and permanently. A superseded ADR is
marked Superseded and points forward; it is never deleted, because the reasoning that was wrong is
part of the record.

| [005](ADR-005-capability-bearer-tokens-cross-process.md) | Should a capability that must cross a process boundary be a self-verifying macaroon-style bearer token, or an opaque reference checked against a host-side registry? | **Judged, narrowly.** Resolves OQ-3. | [007](ADR-007-span-level-taint-vs-per-item.md) | Should taint be tracked at sub-string (span) granularity rather than per-`Content`-item? | **Judged — rejected.** Resolves OQ-5. A span-taint prototype confirmed the precision claim (per-item taint really does deny genuinely trusted material sharing an item with tainted material) but red-team found a naive, otherwise-plausible `concat` implementation silently under-taints real danger bytes on the first attempt — a new security-relevant bug class per-item taint structurally cannot have. The concrete precision gap is already closed today by keeping trusted/tainted material as separate `ContentItem`s (017 §3's existing structural-separation idiom), at the same precision, without that risk. Decision: keep per-item taint (003 §2); do not build span-level taint. |
| [008](ADR-008-wasm3-cold-start-vs-wasmtime.md) | Does wasm3's cold-start advantage over Wasmtime, measured on our own workload, clear the 023-budget bar OQ-12 set before it is even a candidate? | **Judged — the gate clears, the runtime decision is deferred.** Resolves OQ-12. | [012](ADR-012-sandbox-profile-template-parameter-kind.md) | What kind of thing is `SandboxProfile<P>`'s template parameter `P`: an enum value naming a closed set of engine profiles, or any type satisfying `SandboxBackend`? | **Judged.** `P` is any type satisfying the new `SandboxProfileArg` concept — a real `SandboxBackend`, or the resolution selector `Strict` (replacing the independently-broken, undefined `Profile::Strict`) — never an enum value; 008 §2a's extensibility promise made true by construction. | [013](ADR-013-https-egress-tls-client.md) | Where does the egress proxy's TLS client come from, and how is the dependency vendored, given 008 §10 Q3 draws the "needs a vetted crypto library" line at TLS specifically? | **Judged.** mbedTLS vendored directly (3.6.7, exact-pinned + checksummed via `FetchContent`, this project's own established discipline — not Quark's laxer vcpkg-floor `QUARK_WITH_MBEDTLS` path), behind `AGENTENGINE_WITH_HTTPS` (default off). `TlsClientSession` provides real system-CA-style validation (a separately-pinned, compiled-in CA bundle) and real hostname verification, unlike Quark's `SecureTransport` (deliberately nulled-out hostname check for cluster mTLS, re-confirmed unsuitable). Proven with in-memory-generated test certificates against a real loopback TLS server: valid-cert positive control, untrusted-root/hostname-mismatch/expired-cert rejection all confirmed on Windows and Linux. A real Quark header bug (missing `<atomic>` include, Linux-only) was found and fixed on this project's own side (Quark never patched in-tree). Default (HTTPS-off) build/test posture reconfirmed fully unaffected. |
| [014](ADR-014-worktree-mount-path-canonicalization.md) | How does a real, OS-backed materialization of a worktree mount resolve a guest-supplied relative path so that `..`, absolute redirects, symlink/junction/reparse-point crossing, ADS, `\\?\` prefixes, unicode-normalization tricks, and TOCTOU re-resolution can never name anything outside the mount root? | **Judged.** Design A (lexical canonicalize-then-string-check, reopen the checked string later) rejected: a real, deterministically-reproduced TOCTOU proof shows the reopened handle reads content that was swapped in AFTER the check passed. Design B (`open_within_mount_root`, `core/worktree_mount_fs.hpp`) accepted: a single handle-based `CreateFileW` lets Windows resolve reparse points transparently, and containment is verified from the resulting HANDLE (`GetFinalPathNameByHandleW`), never from a re-parsed string — proven immune to the identical interleaving (an already-open handle is unaffected by a later swap; a fresh post-swap request re-resolves and is correctly rejected). A real production bug (missing `FILE_SHARE_DELETE` on the target handle, which would let an open guest handle block a host-side delete/replace) was found and fixed during the same prove pass. 22/22 checks, Windows only — Linux parity (Phase C4), 8.3 short-name aliasing, and real-symlink-vs-junction parity are named, untested residuals, not silently assumed. |
